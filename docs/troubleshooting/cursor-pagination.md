# 커서 기반 페이지네이션 누락 방지 (사전 대응)

- 상품 목록에 커서 기반 페이지네이션을 도입하기 전, `created_at` 단일 커서의 위험을 미리 점검한 기록.
- 버그가 난 뒤가 아니라, **동일 timestamp 데이터에서 누락/중복이 생길 수 있다는 점을 사전에 발견**해 설계 단계에서 막았다.

## 1. 문제 상황 (예상 이슈)

커서 기반 페이지네이션을 `created_at` 컬럼 기준으로 구현할 계획이다. 하지만 동일한 초 단위로 생성된 데이터가 존재할 경우, 다음 페이지 조회 시 **데이터 누락 또는 중복 조회**가 발생할 가능성이 있다.

예를 들어:

- 10번째 데이터의 `created_at`을 커서로 사용
- 동일한 `created_at` 값을 가진 11번째 데이터가 존재하는 경우
  → `created_at > last_created_at` 조건만으로는 해당 데이터를 조회하지 못함

결과적으로 일부 데이터가 페이지네이션 과정에서 누락될 수 있다.

## 2. 원인 분석

커서 기반 페이지네이션은 **정렬 기준이 유일하게 순서를 보장해야 한다**는 전제가 필요하다.

하지만 `created_at` 단일 컬럼은 다음과 같은 한계를 가진다:

- 초 단위 timestamp는 동일 값이 발생할 수 있음
- 동일 timestamp 내에서 데이터 간 순서를 보장할 수 없음
- 결국 "정확한 다음 데이터 위치"를 특정할 수 없음

즉, 정렬 기준이 모호해지면서 페이지 경계가 깨지는 문제가 발생한다.

## 3. 해결

`created_at` 단일 기준이 아닌 **복합 커서 전략(`created_at + id`)** 을 적용한다.

`id`는 유일(PK)하므로, 동일 `created_at` 안에서도 순서를 확정할 수 있는 **타이브레이커** 역할을 한다. 이를 통해 항상 유일한 다음 커서 위치를 보장한다.

## 4. 구현 내용

### (1) 정렬 기준

```sql
ORDER BY created_at DESC, id DESC
```

### (2) 커서 조건 — 행 값(row-value) 비교

커서 기반 페이지네이션에서는 "이전 마지막 데이터 이후의 모든 데이터"를 정확히 가져오는 것이 중요하다. `created_at`과 `id`를 함께 비교해야 하는데, 이를 표현하는 두 가지 방법이 있다.

먼저 논리를 그대로 풀어 쓰면 다음과 같다.

```sql
WHERE
  (created_at < last_created_at)
  OR
  (created_at = last_created_at AND id < last_id)
```

- **1차 기준 `created_at`** — 더 오래된 데이터만 다음 페이지로 이동
- **2차 기준 `id`** — 동일한 `created_at` 내에서는 `id`로 순서를 결정

다만 이 `OR` 형태는 Postgres가 두 개의 인덱스 스캔(`BitmapOr`)으로 풀고 뒤에 별도 `Sort`를 붙여, 복합 인덱스의 정렬을 그대로 살리지 못한다. 그래서 **논리적으로 완전히 동일한 행 값 비교**로 작성한다.

```sql
WHERE (created_at, id) < (last_created_at, last_id)
```

이 형태는 복합 인덱스 순서와 1:1로 매칭되어 **단일 정렬 Index Scan**으로 실행된다.

### (3) 복합 인덱스 설계

항상 `group_id`로 먼저 거른 뒤 커서로 정렬하므로, **`group_id`를 선두에 둔** 복합 인덱스를 만든다.

```sql
CREATE INDEX idx_products_group_cursor
ON products (group_id, created_at DESC, id DESC);
```

- `group_id`가 선두라 `Filter`가 아닌 `Index Cond`로 처리된다.
- 이어지는 `created_at DESC, id DESC`가 정렬을 보장해 별도 `Sort`가 사라진다.

> **인덱스는 정확성이 아니라 성능을 위한 것이다.** 누락·중복 없는 결과는 `ORDER BY created_at, id` + 행 값 비교가 보장한다(인덱스가 없어도 결과는 맞다). 인덱스는 매 페이지마다 전체를 정렬하지 않고 **커서 위치로 바로 점프**하게 해, 대용량에서도 일정한 성능을 유지시키는 역할이다.

## 5. 결과

단일 커서와 복합 커서의 차이를 정리하면 다음과 같다.

| 구분                  | 단일 커서 (`created_at`)     | 복합 커서 (`created_at + id`)  |
| --------------------- | ---------------------------- | ------------------------------ |
| 동일 timestamp 데이터 | 누락/중복 가능               | 항상 유일하게 정렬             |
| 다음 위치 특정        | 불가능(모호)                 | `id` 타이브레이커로 확정       |
| 인덱스 활용           | 정렬 순서와 불일치 시 비효율 | 복합 인덱스로 정렬·조회 최적화 |

- `created_at`이 겹치는 데이터가 여러 건이어도 페이지 경계에서 누락/중복 없이 조회된다.
- 정렬 기준과 인덱스가 일치해 대용량에서도 안정적인 성능을 유지한다.

## 마치며

이번 건은 버그를 겪고 고친 게 아니라, **설계 단계에서 "동일 시각 데이터"라는 엣지 케이스를 미리 떠올려** 막은 사례다. 커서 페이지네이션은 "정렬 기준이 유일해야 한다"는 전제가 깨지는 순간 조용히 데이터가 새기 때문에, 정렬 키에 PK 같은 유일 컬럼을 타이브레이커로 함께 두는 습관이 중요하다는 걸 정리해 둔다.
