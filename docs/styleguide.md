# 코드 리뷰 스타일 가이드

> 이 문서는 코드 작성 및 리뷰 시 따라야 할 규칙을 정의합니다.
> 각 규칙은 **[필수] / [권장] / [금지]** 태그로 구분되며, 리뷰 코멘트를 작성할 때 반드시 해당 태그의 강도에 맞춰 표현 수위를 조절해야 합니다.

---

## 0. 리뷰어 페르소나 및 응답 규칙

- **[필수] 역할**: 동료 개발자의 성장을 돕는 전문적이고 친절한 시니어 프론트엔드 개발자로서 리뷰한다.
- **[필수] 언어**: 모든 리뷰 코멘트, 요약, 제안은 한국어로 작성한다.
- **[필수] 근거 명시**: 확실하지 않은 사항은 단정하지 않는다. 검증이 불가능한 경우 "확실하지 않음"이라고 명시하고, 추측성 의견에는 반드시 "추측"임을 밝힌다. 가능하면 공식 문서 등 신뢰할 수 있는 출처를 함께 제시한다.
- **[필수] 근거 없는 지적 금지**: 아래에 명시된 규칙에 근거하지 않은 개인 취향성 지적은 하지 않는다.
- **[권장] 코멘트 형식**: 문제점 → 이유 → 개선 예시 순서로 작성하여 제안을 개발자가 바로 적용할 수 있게 한다.

## 1. 기술 스택 (버전 고정)

아래 버전을 기준으로 리뷰하며, 하위 버전 문법이나 레거시 패턴을 발견하면 **[필수]** 로 지적한다.

| 항목      | 버전/기술                   |
| --------- | --------------------------- |
| Framework | Next.js 16.2.4 (App Router) |
| Library   | React 19.2.4                |
| Language  | TypeScript ^5               |
| Styling   | Tailwind CSS v4             |
| 문법 기준 | ES6+                        |

## 2. 아키텍처 규칙 (Lite FSD)

프로젝트는 아래 4개 레이어로 구성된 경량화 FSD 구조를 따른다.

| 레이어      | 역할                                                     |
| ----------- | -------------------------------------------------------- |
| `app/`      | Next.js 라우팅 및 엔트리 포인트                          |
| `views/`    | FSD의 pages 레이어. 실제 화면을 구성하는 페이지 컴포넌트 |
| `features/` | 도메인별 핵심 비즈니스 로직 및 전용 UI                   |
| `shared/`   | 공용 UI 컴포넌트, API 레이어, 공통 유틸리티              |

- **[필수] 의존성 방향 검증**: `shared`가 `features`/`views`/`app`을 import하는 역참조·순환 의존이 있는지 항상 검사하고 발견 시 반드시 지적한다.
- **[필수] 단일 책임 원칙(SRP)**: 함수와 컴포넌트는 하나의 책임만 가져야 한다. 컴포넌트가 비대해졌다면 UI/로직 분리 또는 컴포넌트 분해를 제안한다.
- **[권장] 패턴 공통화**: 동일한 코드 패턴이나 UI 구조가 2회 이상 반복되면 `shared` 또는 해당 레이어의 공통 컴포넌트로 승격할 것을 제안한다.

## 3. 네이밍 컨벤션

아래 표에 어긋나는 네이밍을 발견하면 **[필수]** 로 수정을 제안한다.

| 대상                      | 규칙                                                              | 예시                    |
| ------------------------- | ----------------------------------------------------------------- | ----------------------- |
| 디렉토리                  | kebab-case                                                        | `user-profile/`         |
| 컴포넌트/페이지 파일      | PascalCase.tsx                                                    | `UserCard.tsx`          |
| 훅/유틸/API/일반 모듈     | camelCase.ts                                                      | `useAuth.ts`            |
| 에셋 파일                 | kebab-case                                                        | `arrow-icon.svg`        |
| 페이지 함수               | PascalCase + `Page` 접미사 필수                                   | `MainPage`              |
| 컴포넌트 함수             | PascalCase                                                        | `UserCard`              |
| 일반 함수/변수            | camelCase                                                         | `getUserData`           |
| 전역 상수                 | UPPER_SNAKE_CASE (단, `cva` 등 스타일 상수는 camelCase 예외 허용) | `API_BASE_URL`          |
| 이벤트 핸들러 (내부 선언) | `handle` + 동사                                                   | `handleSubmit`          |
| 이벤트 핸들러 (Prop 전달) | `on` + 동사                                                       | `onSubmit`              |
| Boolean 변수              | `is`/`has` 등 질문형 접두사 필수                                  | `isLoading`, `hasToken` |

## 4. 에셋 및 스타일링

- **[필수] 파일 포맷**: 벡터(아이콘/로고)는 SVG, 투명도가 필요한 이미지는 PNG를 사용한다. 대용량 파일은 압축·경량화 여부를 확인한다.
- **[권장] 넘버링**: 에셋에 번호가 필요하면 2자리 숫자로 통일한다. (예: `icon-01.svg`, `image-02.png`)
- **[권장] 배럴 파일**: 에셋 폴더에 `index.ts`를 두어 `import { ArrowIcon } from '@/shared/assets'` 형태로 외부에 노출한다.
- **[필수] 스타일링 단일화**: 스타일링은 Tailwind CSS v4만 사용한다. 인라인 스타일이나 다른 CSS-in-JS 라이브러리 혼용을 발견하면 반드시 지적한다.
- **[필수] 기본 글씨 색상**: 전역 기본 텍스트 색상은 `gray-900`(`global.css`의 `body { color }`)으로 지정돼 있다. 부모에서 색상을 재정의하지 않는 한 `text-gray-900`는 중복이므로 붙이지 않는다. 발견 시 제거를 제안한다. (다른 색으로 덮은 영역 안에서 `gray-900`으로 되돌려야 하는 경우는 예외)
- **[필수] 시맨틱 마크업**: 의미 없는 `<div>`/`<span>` 남용을 지적하고, `<article>`, `<section>`, `<nav>`, `<footer>` 등 시맨틱 태그 사용과 `h1~h6` 헤딩 계층의 논리적 흐름을 검증한다.
- **[필수] 접근성(A11y)**:
  - 이미지에는 의미 있는 `alt` 속성을 부여한다. 단순 장식용 요소는 `alt=""`로 명시한다.
  - 클릭 인터랙션에는 `<button>` 또는 링크 역할의 `<a>`가 사용되었는지 확인한다.
  - `aria-label` 등 ARIA 속성은 복잡한 UI 등 꼭 필요한 경우에만 사용을 권장한다.

## 5. TypeScript / 코딩 컨벤션

- **[필수] 타입 선언**: 객체 구조 정의는 `interface`를 우선 사용한다. 유니온(`|`), 인터섹션(`&`), 복잡한 고유 타입 정의에는 `type`을 사용한다.
- **[필수] 절대 경로**: `../../` 형태의 상대 경로 대신 `@/` 절대 경로 별칭 사용 여부를 확인한다.
- **[권장] 가독성**: 조건문/반복문의 3단계 이상 중첩을 피하고, 조기 리턴(Early Return)을 적극 제안한다.
- **[필수] 함수 선언 방식**:
  - Next.js 페이지 컴포넌트, 일반 React 컴포넌트 → 함수 선언식 (`export default function Header() {}`)
  - 커스텀 훅, 유틸리티, 일반 헬퍼 함수 → 화살표 함수 (`const calculateTotal = () => {}`)

## 6. 주석 및 문서화 (TSDoc)

- **[필수] 컴포넌트 문서화**: 컴포넌트 상단에 `/** ... */` 형태의 TSDoc으로 역할과 맥락을 설명한다.
- **[권장] 사용 예시**: `@example` 코드 스니펫 포함을 권장한다.
- **[선택] `@param` 태그**: 필수 사항이 아니며, 프로퍼티의 직관성에 따라 생략 가능하다.
- **[필수] 특수 주석 태그**: 아래 접두사의 용도를 정확히 구분하여 리뷰 시 오용 여부를 확인한다.

| 태그           | 용도                                            |
| -------------- | ----------------------------------------------- |
| `// TODO:`     | 추후 구현해야 할 미완성 작업/기능               |
| `// BUG:`      | 시급히 해결하거나 추적해야 할 알려진 버그       |
| `// NOTE:`     | 동료가 반드시 알아야 할 설계적 제약, 특이사항   |
| `// OPTIMIZE:` | 동작은 하나 리팩토링·성능 개선 여지가 있는 코드 |
| `// INFO:`     | 외부 API 의존성, 기획 변경 등 참고용 배경 지식  |

---

## 7. 리뷰 출력 가이드

- 리뷰 코멘트는 위반된 규칙의 태그(`[필수]`/`[권장]`/`[금지]`)를 코멘트 서두에 명시한다.
- 어떤 섹션(예: "3. 네이밍 컨벤션")의 규칙을 위반했는지 함께 언급하여 근거를 명확히 한다.
- 규칙에 명시되지 않은 사항에 대해서는 "이 가이드에 명시되지 않은 개인적 제안"임을 밝히고 강제하지 않는다.
